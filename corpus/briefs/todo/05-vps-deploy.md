# Task 05: Container, VPS stack, Ward entry and the owner's docs

## Context

The board moves off the owner's machine and onto the shared VPS, like
almanac. Caddy serves the built board at `/brief-board/` and forwards
`/brief-board-api/` to the API container on `127.0.0.1:8806`. That is the
same port the server uses locally, and no stack on the box uses it. Almanac's
deploy work is the model: `infrastructure/` in its repo, `stacks/almanac.ts`
in vps-deploy, and its `docs/owner-setup.md`.

Deploying, pushing and creating secrets are owner steps. Write the commands
down and never run a deploy.

Depends on 02, 03 and 04.

- `infrastructure/Dockerfile`, `infrastructure/docker-compose.yml`,

- `docs/owner-setup.md` (new), `README.md`

## What to do

1. **Container.** Copy almanac's `infrastructure/Dockerfile` and
   `docker-compose.yml`.
   - Service `brief-board-api`, image `brief-board-api:1.0`, published on
     `127.0.0.1:${BRIEF_BOARD_PORT:-8806}`.
   - `env_file: .env`. Remember that the compose `environment:` block beats
     `env_file`.
   - `HOST=0.0.0.0`, `BRIEF_BOARD_DB=/data/brief-board.sqlite`, `VOLUME
     /data`, a data bind mount `${BRIEF_BOARD_DATA_DIR:-../data}:/data`, and
     the wget health check on `/api/health`.
   - The image holds `shared`, `server` and `server/vendor`, plus every
     workspace manifest the lockfile needs. It doesn't hold the CLI or the
     web source, because Caddy serves the built board.
   - Build it with `docker build` if Docker is reachable, and say so if it
     isn't.
2. **The stack.** Copy `stacks/brief-board.ts` from `stacks/almanac.ts` as a
   `WebServiceStack`, with a header comment in the same style. Settings:

   | Setting | Value |
   |---|---|
   | `basePath` | `/brief-board` |
   | `apiPrefix` | `/brief-board-api` |
   | client `distDir` | `web/dist` |
   | client remote dir | `/var/www/brief-board` |
   | client `baseEnv` | `BRIEF_BOARD_BASE` |
   | `tryFiles` | `spa` |
   | server dir | `/srv/brief-board-api` |
   | service, port | `brief-board-api`, 8806 |
   | health check | `/api/health`, expecting `"ok":true` |
   | `requireLoopback` | on |

   Persistent state is the data directory, and it "holds every ticket,
   comment and move, and the accounts' password hashes". Declare
   `BRIEF_BOARD_TOKEN` as a required secret of the stack, with the hint
   "openssl rand -base64 32; the same value goes in
   ~/.config/brief-board/env on the owner's machine". Pass it into the
   container's environment.
3. **Register it.**
   - In `lib/estate.ts`: `briefBoard: new SourceRepo(this,
     "brief-board-repo", { repo: "brief-board", workspaceRoot: true })`.
   - In `app.ts`: the construction, `useWard(ward.identityFor(briefBoard,
     "brief-board"))` with the other Ward clients, and the trailing list.
   - Run `node cli.ts synth` and `node cli.ts --check`. Both must pass.
   - Update the listings: the row in `docs/stacks.md`, and the stack counts
     in its first line and in the README.
   - Commit in vps-deploy on `main`: one commit, no push. If the commit is
     refused, leave the change uncommitted and say so.
4. **Revisit "A down board never stops work"** in `decisions.md`, with a
   `log.md` line naming the revisit. The always-on container with a restart
   policy, rejected on 2026-10-08, is now what runs. What stays: the CLI exits
   3 when it can't reach the board, agents carry on, moves made while it's
   down are lost, and sync recovers them.
5. **`docs/owner-setup.md`.** Copy almanac's structure and use `<production
   origin>` for the address:
   1. Register the board in production Ward. Open the console on Ward's own
      host and sign in as the break-glass superuser. Create the app with
      slug `brief-board` and public registration closed. Make the key pair
      with `npm run oidc-client-key --workspace=api -- brief-board` in Ward's
      checkout. Register the client with the redirect URI `<production
      origin>/brief-board-api/auth/ward/callback` and the sign-out return
      `<production origin>/brief-board/`.
   2. Write the deploy secrets: `secrets/brief-board.env` in vps-deploy with
      `WARD_OIDC_CLIENT_KEY` and `BRIEF_BOARD_TOKEN`, then `chmod 600`.
   3. Check the container locally against a scratch data directory.
   4. Deploy: `node cli.ts brief-board all --dry-run`, then without
      `--dry-run`. Check the stack's CLI name in `cli.ts`. Then the two curl
      checks.
   5. Create your account: the seed inside the container, over the services
      account, as almanac's step 5 does it.
   6. Grant your Ward account. Sign in with the local account first, then
      link Ward from the account page, or you end up with two users.
   7. Point the CLI at the VPS. In `~/.config/brief-board/env`, set
      `BRIEF_BOARD_URL=<production origin>/brief-board-api` and the same
      `BRIEF_BOARD_TOKEN`, then `chmod 600`. Check with `brief-board list`,
      then run `brief-board sync`.

   Add a "Local development" section: `.env` from `.env.example`, the seed,
   the local Ward seed, `npm run dev`.
6. **README.** The status line says the board runs on the VPS behind
   sign-in, and locally for development. Today it says there's no hosted
   copy. Link `docs/owner-setup.md`.
7. **Wiki.** "Running it" in `architecture.md` and the snapshot in
   `status.md`.
